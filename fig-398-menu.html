1基準是工作區時沒有「含未 commit」勾選框 —— 整頁本來就是未 commit 的變更,那個勾選框在這裡沒有東西可以切。面板維持「已暫存 / 變更」兩塊,只有提交訊息框和提交/推送退場。
2基準跟著分頁活著,只在 session 内。分頁不存在時,面板那顆鈕新建一個,基準用該 repo 記住的那個,沒設過才是工作區 —— 若新建時永遠重設,「記住」就永遠看不到效果;分頁已經在但不在前景時,那顆鈕是聚焦,基準不動 —— 聚焦不該改掉你正在看的東西。app 重開就回到工作區,不做持久化。
3只有帶著意圖的入口才會換基準。Git Graph 的「開啟這個 commit 的變更」、「比較這兩個」—— 這些話裡本身就有基準,所以進來要換,就算 singleton 分頁被重用也一樣(#398 已定)。面板那顆鈕沒有這種意圖,它只是通道。
4按 repo 記,不是全域記一個。基準是 upstream/main 這種 ref 名字,而 ref 跟著 repo 跑 —— 換到別的資料夾,那個 ref 可能根本不存在,936578d..2db2298 更是一定不在;就算有同名分支,意思也不同。頁面本來就有這條線:AllChangesTabContent.tsx:157 那個 effect 依 rootPath,換資料夾就重解 repo、repo 一變就重掃。
5兩個邊界情況。ref 不見了(git branch -d、遠端被移掉、追蹤取消設定)—— 退回工作區並講一聲,不要卡在錯誤畫面上;這比換 repo 容易發生,因為分頁開著的時候你可能就在旁邊的終端機刪分支。worktree —— 同一個 repo 的不同 worktree,refs 共用但工作區不同,所以 key 要用 gitResolveRepo 解出來的那個路徑,不要用 git common dir。
6解得出名字的才記:分支和 tag 記,裸 hash(936578d)和範圍(A..B)不記。名字是「以後還會有意義」的承諾,hash 只是一張快照;而且 commit 會不見 —— rebase 或 amend 一下就沒了,同一個 session 内就會發生。範圍在分頁活著時當然留著(那是分頁的狀態),但不寫進 repo 的記憶;新開一頁時退回上次記住的那個 ref,沒有就工作區。
