Git Graph 欄寬階梯

常見情況一個像素都不動:六條 lane 以內,維持今天的 14px 欄寬和 124px gutter。 超過才進入第一段補救——收窄欄寬,而且一路到九條都還塞得進同一個 124px。 只有連 9px 都撐不住,才真的把 gutter 加寬。

01三段式

gutter 的寬度就是 欄數 × 欄寬 + 40(paddingLeft 16 加尾端 24), 今天的 6 × 14 + 40 = 124。把 124 當成預算,三段的規則是: 

const GUTTER_BUDGET = 124;  // 今天的寬度,就是預算
const LANE_MAX = 14, LANE_MIN = 9;

function laneSizing(lanes) {
  // 第一段:塞得下就什麼都不改
  if (lanes * LANE_MAX + 40 <= GUTTER_BUDGET) return LANE_MAX;
  // 第二段:收窄欄寬把它塞回預算裡,但不低於下限
  return Math.max(LANE_MIN, Math.floor((GUTTER_BUDGET - 40) / lanes));
}
// 第三段不必寫:欄寬碰到下限之後,gutter 自然就是 lanes * 10 + 40

第二段是免費的。7 條收到 12px、8 條 10px、9 條 9px,三者都還在 124px 之內—— 比今天多三欄,而 gutter 一格都沒有多要。真正付出寬度的只有第三段, 而那時候的替代方案是把三條線疊在同一欄。

第三段還有第二筆代價:顏色不夠用

BRANCH_COLORS 只有 7 個。pickColor 會主動避開 仍然活躍的鄰居,所以在 7 條以內,同時活著的 lane 保證不同色—— 但超過之後調色盤就用完了,只能退回計數器、接受重複。

這比多幾個像素嚴重得多,因為 git graph 的顏色是識別符: 兩條同時活著的分支同色,就沒辦法靠顏色追蹤其中一條,而那正是這張圖最主要的用途。 所以第三段是雙重降級——gutter 變寬,而且顏色開始說謊。

這也是為什麼第二段值得盡量撐:9 條 lane 還在預算內、也還在調色盤的容忍範圍邊緣。 真正的建議是用分支篩選把同時顯示的分支控制在 7 條以內, 第三段只是「真的塞不下時不要畫錯」的保底,不是一個好狀態。

02三段各自長什麼樣

同一種歷史,只是分支數不同。三張跟著下一節的滑桿走, 所以調參數的時候三段會一起變——同一組值在六條和十一條都要成立, 不能只調到其中一種好看。

03拉分支數看它怎麼走

第一根滑桿是分支數——欄寬、gutter、走到哪一段都是策略算出來的。 下面三根是畫法:轉到你要的樣子,底下那行就是可以直接抄進 edgePath 的公式。

上限那根獨立出來是有原因的:彎折高度跟著水平距離走,一條 lane 的小跳沒問題, 但從第 11 欄併回主幹是 90px 的水平距離,乘上倍率就會變成一條四五列高的巨弧。 上限讓長跳單純畫成它本來就是的那條斜線。

讓位開關幾乎看不出差別,那不是 bug

這份歷史裡只有 fix/quick-hotfix 那一條會受影響——它一個 commit 就併回主幹, 空出第 1 欄,右邊那條才有地方可以補上去。其餘十條分支全部在最上面開、 全部在最下面收,中間沒有任何欄位空出來過,自然也沒有讓位可做。

底部那幾列雖然有洞,但那時剩下的 lane 都快結束了,「快結束的不搬」那條規則會正確地擋掉—— 不擋的話會織成一團。

而這正是它省不到欄寬的原因:欄數由尖峰決定,尖峰在最上面, 那裡一個欄位都還沒空出來。讓位是視覺選項,不是省空間的手段。

04實作上要注意的三件事

寬度要從整份載入的歷史算,不是可視範圍

Git Graph 是分頁載入的。如果用畫面上看得到的那幾列去算最大 lane, 捲動時 gutter 會跟著抽動。應該用已載入的整個 commit 集合算, 而且一個 session 內只增不減——載入更多歷史發現有第 10 條 lane 就加寬, 但捲回去不要縮回來。

那個寫死的 6 要一起換掉

GitGraph.tsx 目前把欄寬寫成 paddingLeft + 6 * laneWidth + 24。那個 6 是 maxLane + 1 的重複,不跟著改的話,gutter 的寬度會和實際畫出來的內容對不上。

側邊欄的精簡圖不吃這個策略

commitGraph.ts 的 maxLane: 2 是窄窗格刻意的設定, 不該被自適應覆蓋。geometry 必須繼續當參數傳——現在的設計已經是這樣,保持住就好。
