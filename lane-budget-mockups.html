Git Graph 的 Lane 預算

maxLane = 5 不是 lane 演算法的上限,而是「畫」的上限。第 7 條之後的分支線 被夾到同一個 x,疊在一起——而且因為有兩處邏輯拿 x 座標當 lane 相等的代理,這個純視覺的截斷 會悄悄弄壞 merge 彎折與鍵盤導覽。以下是同一份 18 個 commit、8 條 lane 的歷史,在幾種幾何 設定下實際畫出來的樣子——圖是跑真的 computeGraphLayout 規則算的,不是示意圖—— 後面接各家工具怎麼處理同一個問題,包含一個有人做過、測過、然後拒絕的方案。

6 欄 → 8 欄
把欄寬從 14px 收到 10px、欄數放到實際用量,gutter 從 124px 變成 120px——多兩欄,而且比現在還窄 4px。

01現況會畫成什麼樣

這份歷史有 8 條同時開著的分支線——就是你這個 repo 現在的狀態,一堆還沒合併的 feature 分支。lane 6 和 lane 7 被 Math.min(lane, maxLane) 夾到和 lane 5 同一欄。

現況/ maxLane 5 · laneWidth 14px · gutter 124px

三條不同顏色的線畫在同一條軌道上,後畫的蓋掉先畫的。顏色其實有 7 個,夠用—— 瓶頸是幾何,不是調色盤。

02截斷不只是難看,它在說謊

上圖第 7 列那個 merge 是關鍵。f6f0754 在 lane 6,把 lane 7 的 a203eff 併進來。兩者的 x 被夾成相同,於是:

截斷後(現況) 直線 彎折消失,看起來像同一條線上的父節點
應該長這樣 彎折 lane 6 的 commit 併入 lane 7 的分支

原因在 graphLayout.ts 兩處都用 x 相等判斷 lane 相等: edgePath 的 if (px === cx) 走直線分支; laneContinuationRowIndex 用 e.cx === e.px 找「同一條 lane 的延續」。 後者餵的是 GitGraph.tsx:249 的鍵盤導覽——所以 Shift+↑/↓ 會沿著這條不存在的直線跳到錯的 commit。

修法與視覺無關,而且該先做:GraphEdge 已經帶了子節點的 lane,補一個 parentLane,兩處改成比 lane index。截斷就退回成純視覺,永遠不會對邏輯說謊。

05彎折:改一個常數

lane 讓位:參考畫面裡那條往左跳的線

參考畫面裡綠色那條在中間往左移了一欄。那不是彎折——那是 lane 讓位:上面那條只有單一 commit 的分支匯回主幹、空出第 1 欄之後, 綠色那條整條滑進去繼續往下走。

現在的演算法做不到這件事。computeGraphLayout 的 lane 一旦配定就固定, slot 被釋放之後只會等下一條新分支來認領, 已經在跑的分支不會搬過去。左右兩張是同一份 commit、同樣的兩列彎折,只差有沒有讓位:

現況/同樣彎折 · lane 配定就不動左邊留一個空欄
加上讓位/空出來就有人補上參考畫面的行為

這跟 SourceGit 拒絕的 lane merging 不是同一件事:讓位不合併任何線, 每條分支仍然自己一條、自己一個顏色,只是換了欄位。

但它省不到任何欄寬

欄數由尖峰決定,而尖峰在圖的最上面:分支的 tip 一條接一條 claim 新欄位,那時候還沒有任何 lane 被釋放,沒有洞可以補。讓位只在有東西結束之後才生效, 也就是圖的下半部——但 gutter 的寬度早就被上面那段決定了。

第 04 節的讀數就是證據:那份歷史開 8 條 lane,勾不勾讓位都是 「8 條(讓位前 8)」。它讓下半部看起來收攏, 卻一格欄寬都省不下來。

而「分支都沒合併、tip 全擠在最上面」正是這個 repo 的形狀—— 也就是說,在最需要它的情況下,它剛好幫不上忙。

它有三條規則不能省,少一條就會畫成一團——列在這裡是因為它們是這次探索真正的產出, 而不是因為建議做: 一、往最近的欄位收,不是拉最右邊那條過來補洞(那會讓一條線橫跨半張圖); 二、不跨過留在原地的線,寧可讓欄位空著也不要兩條線交叉; 三、快結束的 lane 不搬,而且「快結束」要看那條 lane 的 run 還剩多長, 不是看下一個 commit 有多近——後者在密集分支上永遠是一兩列,等於把整個讓位關掉。 第三條需要一個前置掃描先走完整份歷史, 這也是它唯一動到架構的地方:現在的 computeGraphLayout 是單趟、純局部的。

它有三條規則不能省,少一條就會畫成一團: 一、往最近的欄位收,不是拉最右邊那條過來補洞(那會讓一條線橫跨半張圖); 二、不跨過留在原地的線,寧可讓欄位空著也不要兩條線交叉; 三、快結束的 lane 不搬——剩不到四列就要匯回主幹的線, 橫移一次再結束純粹是噪音,而圖的底部正是一堆線同時結束的地方, 每條都搬一次就會織成一個結。

真正的問題不在係數,在公式綁錯了東西。 edgePath 現在寫的是 Math.min(rowHeight, py - cy)—— 彎折的高度跟著列高走。可是一次換道的水平距離是欄寬, 兩者無關:36px 高、14px 寬的 S,長寬比 0.39,不管控制點怎麼調都像一條斜直線。 拉成兩列只會變成 72 高 / 14 寬,更平。

量參考畫面也印證了這件事:它的欄距 27px、彎折垂直跨約 55px, 長寬比 0.49——比現況「彎」得多,而不是比較長。

所以規則應該是彎折高度跟著水平距離走:

const bend = Math.min(Math.abs(px - cx) * 1.6, py - cy);

這樣曲線的形狀是恆定的:列高改了不影響、欄寬收窄也不影響、 跨一條 lane 和跨四條 lane 的 merge 弧度一致。上面用 1.6×,長寬比 0.63。 min 一樣負責「空間不夠就自動縮短」。

起彎時機是第二個、獨立的參數,而且它不影響水平推進—— 兩個控制點各自跟著自己端點的 x,橫向永遠是同一條 smoothstep。它改的是垂直配速: 係數大 = 先貼著自己的欄位再急轉;係數小 = 一離開節點就往外畫。上面用 0.42。

它跟欄寬收窄是同一個決定的兩半。欄寬 10px 表示一次換道的水平位移只有 10px; 如果在一列 36px 之內走完,斜率接近垂直,看起來就是一條直線—— 只改欄寬不改彎折,換來的是一張分不出換道的圖。

空心環則不建議

下面第三欄是空心環的樣子,放在這裡是因為評估過、結論是不要。 理由不是不好看,是兩件具體的事。

10px · 現況畫法 尖角 彎折擠在一列內,實心點
10px · 加大彎折 兩列 弧線放緩,節點不變
10px · 加大彎折 ＋ 空心環 不建議 花掉一個已經有意義的區別

一、它要解決的碰撞不存在。一列只有一個 commit,所以節點跟節點永遠不會在 水平方向相撞。真正的鄰居是隔壁 lane 那條線:節點 r=5.5 加 2px 背景色描邊, 外緣到 10px 外的鄰線還有 3.5px,而那圈背景色描邊本來就是為了在線上挖出護城河。 實心節點在 10px 下沒有問題。

二、「空心」在這個 app 裡已經有意義了。#399 的工作區那一列用的就是空心虛線環, commit message 寫得很明白:hollow with a dashed ring so it reads as neither of the filled kinds。每個 commit 都變空心之後,那個區別就塌了—— 工作區節點只剩虛線這一個弱得多的訊號。填實與空心是這張圖上少數還沒被用掉的對比, 拿去換一個不存在的碰撞不划算。

至於 edgePath,它現在把彎折限制在 Math.min(rowHeight, py - cy)—— 最多一列。改成兩列是一個常數的事,不影響任何寬度計算。

06各家怎麼處理

這是個公認的難題:分支共用同一個 parent 時會在圖上某處堆積,把圖橫向撐開。 實務上看得到三種策略,加上一種攻擊成因的做法。

VS Code Git Graphmhutchie · 你 mockup 的方向參考
自動撐開,但限制到不會遮住其他欄。issue #197 的原話是「in large repositories the graph can become too wide when the table is automatically laid out, such that it hides some of the other columns」,結論是「it should automatically limit its width so that it doesn't hide any other columns」。已實作,milestone v1.18.0。 = 方案 b。同一個問題、同一個答案,而且是你已經在參考的那個工具。
SourceGitlane merging · 做了,然後拒絕
issue #740 提議把共用同一個 parent 的 lane 合併(GitExtensions 的做法), 讓分支只從真正分岔處才占欄位。維護者真的實作出來測了——用 AvaloniaUI/Avalonia,同一個 revision 上掛著 13 條分支——結論是 「I don't think it's any clearer with merge branch lines enabled」, issue 關成 not-planned。兩個理由:

一、顏色變成歧義。每條分支線有自己的顏色,線被合併後,顏色變化必須先判斷 是真的 merge commit 還是只是兩條線被視覺上併起來—— 「this is not to simplify the problem, but to complicate the problem」。
二、橫線干擾判讀。難以一眼看出某個 commit 在哪條分支上,同樣得先做那個消歧義。 = 方案 e。有人替我們做過實驗了,結果是負的。
SourceGit / Forkshort link curve · 實際採用的規則
同一串討論裡,維護者說明了他們現在的規則:merge commit 和它的 第 2/第 3 個 parent 之間如果沒有其他 commit,就用一條 短連接曲線帶過去,不給它獨立的 lane;有其他 commit 才給獨立 lane。只對 merge 節點、 只對非第一個 parent。他補了一句「this design is also used by Fork」。 比 lane merging 窄得多,但兩個工具都在用。省下的正是最常見的那種浪費: 剛開的分支只有一兩個 commit 就併回來,卻整條佔一欄。
gitk / Sourcetree / Forkgrow & scroll
欄數決定寬度,寬到不行就給水平捲軸。最誠實,但在窄窗格裡會把訊息欄擠掉—— 這正是 mhutchie #197 抱怨的情況。
終端機系(tig / lazygit)cell-based
受限於字元格,只能截斷。但終端機的截斷是看得見的——字元互相碰撞, 使用者知道有東西被壓掉了,不會誤以為那是一條真的直線。

重點不是誰做得最好,而是:沒有一家會把不同的 lane 靜靜畫在同一個 x、又繼續假裝它們是分開的。 要嘛撐開,要嘛明示地折疊。目前 tempo-term 的截斷是第三種——無聲的重疊——這才是真正該修的部分。

07建議的順序

  1. 先修 x 相等當 lane 相等。純函式、好測、跟視覺決策無關,而且它現在就在 弄壞 Shift 導覽。獨立成一支 bug fix PR,可以單獨驗證。
  2. 再把欄數改成自適應,欄寬收窄,同時把彎折放大到兩列。從已載入的整個 commit 集合算最大 lane(不是可視範圍,不然捲動時寬度會跳),一個 session 內只增不減。 彎折半徑要跟欄寬一起改——10px 配一列彎折會擠成尖角,兩者是同一個決定的兩半。 順手把 GitGraph.tsx:369 寫死的 6 * laneWidth 換掉——那個 6 是 maxLane + 1 的重複,不一起改寬度就會對不上內容。
  3. lane 讓位不要做。它省不到欄寬——欄數由尖峰決定,而尖峰在圖的最上面, 那裡還沒有任何 lane 被釋放。第 04 節的讀數是「8 條(讓位前 8)」。 加上它需要一個前置掃描(現在的佈局是單趟、純局部的)、 以及三條全靠眼睛才發現的畫法規則,投報率是負的。
  4. lane merging 也不要做。SourceGit 的維護者已經替我們做過實驗:實作出來、 在 13 條分支的 repo 上測、結論是更難讀,關成 not-planned。他的理由(顏色變歧義、 橫線干擾判讀)套在 tempo-term 上完全成立——我們的顏色配置甚至更講究, pickColor 會主動避開仍然活躍的鄰居,這個投資會被合併線直接抵銷。
  5. short link curve 值得單獨評估。merge commit 的第 2 個 parent 若緊鄰其下、 中間沒有其他 commit,就不給它獨立 lane,用一條短曲線帶過。SourceGit 和 Fork 都這樣做。 它省下的是最常見的浪費:開了分支、兩個 commit 就併回來,卻整條佔一欄。 範圍小、不改讀法,適合當獨立 issue。

側邊欄的精簡圖用 commitGraph.ts 的 maxLane: 2,是窄窗格刻意的設定。 所以 geometry 必須繼續當參數傳、不能寫死成常數——目前的設計已經是這樣,保持住就好。
